Hardware comparison of parallelized fits

This is a fixed dashboard published on Nov. 6, 2026, so it might be outdated. See the latest results on the dev dashboard.

Work in progress: this dashboard doesn't have many data points yet. We'll add more later.

This dashboard compares machines getting through many fits in parallel, like a hyper-parameter search with n_jobs=-1 on all the cores of the machine. A bigger machine often brings little to a single fit, but it can run more of them at once.

Each search fits 8 candidatesHyperparameter combinations tried by the search. Each one is fitted and scored on every cross-validation split. on as many CV splitsTrain/test splits of the data used by cross-validation: each candidate is fitted on the train part and scored on the test part. More in the scikit-learn glossary as the machine has physical coresOne hardware core of the CPU. With SMT, it shows up as two logical CPUs.. Bigger machines have more fits to do, but each fit is the same on every machine (same data size and number of trees). So the time per fit compares machines: a 2x speed-upBaseline time divided by the compared time: 2x is twice as fast as the baseline, 0.5x twice as slow. In the detailed results, a noisy speed-up is shown as ~1.5x (5-15% spread over the repeats) or as a range like 1.2-1.9x (more than 15%). means twice as many fits per second.

How to read

Pick a software tab. Below it, each machine has a tab describing the machine and its software environmentOne Pixi environment of this repository: a fixed set of package versions and builds., since versions can differ between machines. To change the baselineThe reference that speed-ups are computed against., open another machine tab and click "Pick as baseline".

There's one color per machine. Each point is one search, and points above the dashed 1x line get through fits faster than the baseline. Hover a point to see its dataset. "fit time" in "Detailed results" is the wall time of the search divided by its number of .fit()Training a model on data. More in the scikit-learn glossary calls. Marker shapes and "Detailed results" work like in the single fit dashboard.

Each machine scores its candidates on its own splits, so metricsScores of the fitted model on held-out data (ROC AUC, R2 score). They check that the compared implementations learn equivalent models. More in the scikit-learn glossary aren't compared. scikit-learn-intelex trees use exact splitsSplits chosen among every distinct value of the feature. here, like scikit-learn.

Findings

On the benchmarked cases:

  • The Xeon server has ~11x the cores of the Intel Core Ultra laptop, and most random forests, extra trees and HistGradientBoosting searches get ~9x to ~13x faster on it. Ridge on year_prediction_msd too, at ~12x to ~13x. With scikit-learn-intelex, random forests and extra trees reach ~13x to ~18x. On that server, its first repeat is up to ~3x slower than the next two, which the median leaves out.
  • Other searches gain less on the Xeon server: ~5x to ~7x for LogisticRegression, ~4x to ~5x for HistGradientBoosting on the small ames_housing dataset, and ~2x to ~3x for Ridge on susy and ames_housing. Even so, these linear models are faster on the server than on the laptop, while a single fit is often slower on the server.
  • RandomForestClassifier on susy stays at ~6x on the Xeon server without scikit-learn-intelex, and it's unstable: its repeats go from ~20 ms to ~50 ms per fit.
  • The Intel Core Ultra desktop has 1.5x the cores of the laptop. Random forests and extra trees are mostly ~2.5x to ~3x faster on it, and HistGradientBoosting ~2x to ~2.5x. LogisticRegression and Ridge on susy stay at ~1x, probably because memory bandwidth limits them (not measured).
  • On the shortest fits, a very big machine doesn't help: Ridge on ames_housing takes ~6 ms per fit on both the desktop and the Xeon server.
