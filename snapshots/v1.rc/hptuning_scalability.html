RandomizedSearchCV outer-parallelism scalability

RandomizedSearchCV has two levels of parallelism: its outer n_jobsParameter setting how many jobs scikit-learn runs in parallel with joblib. -1 means one per CPU. More in the scikit-learn glossary runs candidatesHyperparameter combinations tried by the search. Each one is fitted and scored on every cross-validation split. in parallel, and each candidate can use threadsUnits of execution that share the memory of their process. Each one can run on its own CPU core. itself. This dashboard sweeps the outer n_jobs to check how the two levels interact.

The marker size is the CPU loadMean share of all the machine's CPUs that were busy during the run. 100% means all cores busy. (100% means all cores busy). The line shape tells how the two levels interact:

  • going down as 1/n_jobs: a single fit has little inner parallelism, and the search scales with outer workers;
  • flat: a single fit was likely already using all cores, so outer workers bring nothing;
  • rising: oversubscription, or bad interactions between joblib and the inner threading layer (they don't coordinate).

In general, we expect more outer workers to run in parallel the sequential parts of each fit, so the search gets faster and the CPU load goes up.

Findings

These results match what the models core-count scalability dashboard shows. On the benchmarked cases:

  • More outer workersSeparate Python processes running tasks in parallel. Unlike threads, they don't share memory. make the search faster with a higher CPU load in most cases, as expected. The exceptions are HistGradientBoosting and the linear models on the Xeon server: they get faster while the CPU load goes down. It's unclear why.
  • Ridge and LogisticRegression: outer parallelism helps, but less than one could hope. These workloads are probably memory boundLimited by how fast data moves from memory rather than by computation, so more cores don't help much., so more cores don't help much.
  • HistGradientBoosting: outer parallelism works well on small datasets or on a big machine, because HGB's own threads are counter-productive there (see the HistGradientBoosting thread-scalability breakdown).
  • RandomForest and ExtraTrees: on susy, the curve is mostly flat, as expected since a single fit already uses all cores. On the smaller datasets with preprocessingSteps run before the model, such as encoding categorical columns and imputing missing values., the search still speeds up with outer workers and the CPU load goes up. OversubscriptionMore busy threads than CPU cores. They compete for the cores and the operating system keeps switching between them, which slows everything down. is mostly harmless on the laptop. On the Xeon server, RandomForestClassifier gets up to ~1.8x slower beyond ~22 outer workers.
  • scikit-learn-intelex: oversubscription is harmless on the laptop. On the Xeon server, the search gets up to ~2x slower beyond ~22 outer workers, for the trees and for Ridge.
