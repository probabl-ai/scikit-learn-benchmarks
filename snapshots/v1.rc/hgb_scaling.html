HistGradientBoosting thread-scalability breakdown

A threadUnits of execution that share the memory of their process. Each one can run on its own CPU core. scaling curve shows whether a fitTraining a model on data. More in the scikit-learn glossary got faster, but not why. This dashboard breaks HistGradientBoosting's fit time into its phases (binningMapping each feature to a small number of integer bins (a few hundred at most) before building trees., histogram computationFor each tree node, summing the gradients of the samples in each bin of each feature., split findingScanning the histograms to find the best feature and threshold to split each node.) to see which ones scale.

How to read

There is one tab per machine, buildOne packaging of the same scikit-learn version. Here, builds differ by their BLAS and OpenMP libraries. and thread affinityPinning threads to given CPU cores, so the operating system doesn't move them around. setting, and one stacked bar per workload. The x-axis is the requested thread count (OMP_NUM_THREADSEnvironment variable setting how many threads OpenMP code uses.). If a bar stops shrinking or grows as threads are added, the extra threads bring nothing or cost time, and the segments show which phase is responsible.

Findings

On the benchmarked cases, adding more threads can be highly counter-productive:

  • On the high-end server, the best thread count grows with the workload. The smallest workloads are fastest on 1 thread, medium ones stop scaling after 4 to 8 threads, and the largest after 16 to 64. Past the best thread count, fits get slower, sometimes dramatically: every workload is 2x to 30x slower at 128 or 172 threads than at its best thread count.
  • On the laptop, active waitIdle OpenMP threads spin on the CPU for a while before sleeping, so they start the next parallel loop faster, at the cost of CPU time. matters for small and medium workloads. Without active wait (the conda-forgeCommunity-maintained channel of conda packages. Its scikit-learn can be installed with different BLAS and OpenMP libraries. build), they get several times slower at 8 and 16 threads: for instance, covtype goes from 11s on 4 threads to 38s on 8. With it (PyPIThe Python Package Index, where pip installs packages from. Its scikit-learn wheels bundle their own OpenMP runtime, and NumPy and SciPy bundle OpenBLAS.), they stay roughly flat or keep improving up to 8 threads. The largest workloads scale up to 16 threads either way. For details about active wait, see scikit-learn#34764.
  • We're working on fixing this. With scikit-learn#34935, using all the threads is rarely much slower than the best thread count.
